# Обновление корпуса и панельный сбор

Команды ниже обращаются к публичным страницам Хабра и **не нужны** для
воспроизведения архивных чисел статьи. Новый сбор создаёт другой снимок
счётчиков и требует повторного расчёта результатов.



```bash
python 01_fetch_metadata.py --corpus wide --cutoff 2024-11-09 --output-dir collected/new_run
```

Коллектор использует JSON endpoint Хабра; его формат может меняться. Общая лента разных типов материалов существовала ещё с 2023 года, но реформа 9 ноября 2026 года изменила классификацию публикаций и фильтрацию по форматам. Поэтому прежний фильтр `postType` (исторический отбор статей) нельзя автоматически считать эквивалентным выборке длинных статей после реформы. **В этой версии сетевой сбор заново не выполнялся, совместимость с изменённым API не проверена.** Новый результат нельзя автоматически подставлять в старый анализ: нужно задать границы и использовать `observed_at`, проверить покрытие, состав форматов и обновить манифест входных данных. HTTP-ошибки, предел страниц и причины остановки сохраняются явно. После прерывания обход начинается с первой страницы с сохранением уже полученных ID, поскольку живая пагинация сдвигается.

## Что проверить перед сбором новой выборки

1. На небольшой пробе проверить поля и значения `postType` / формата в ответах
   API и явно определить критерий включения длинных статей и коротких постов.
   Историческую разметку и новую классификацию хранить отдельно.
2. Сохранять версию правила отбора, момент `observed_at`, хаб и формат.
   При анализе плотности показывать отдельно историческую плотность статей
   выбранных хабов и доступный поток публикаций всех форматов.
3. Для панели повторно запрашивать по ID материалы, выбывшие из свежего
   обхода, проверяя квоты запросов и возможные изменения API. До этой
   доработки полнота горизонтов 1/3/7/30 дней не гарантируется.
4. Строить сравнения по одинаковому горизонту просмотров и сопоставимым
   форматам. Простое сравнение до/после 9 ноября не оценивает причинный
   эффект реформы.

Это рекомендации для будущего сбора, **не выполненные изменения кода**
текущего релиза. Подробности — `docs/reproducibility.md` и раздел 13 статьи.

## Сетевые инструменты вне заморозки

Оба инструмента — опциональные шаги поверх замороженного среза; `run_analysis.py` и тесты сети не касаются.

```bash
# проба: 20 статей из манифеста, сравнение метрик со снапшотом
python fetch_texts.py --limit 20
# полная выгрузка 1600 текстов (~20 минут) -> data/lex_texts_refetched.jsonl.gz
python fetch_texts.py
```

`fetch_texts.py` — проверка методики извлечения на живых страницах: живой текст мог быть отредактирован после снапшота, поэтому ожидается не побайтовое совпадение, а близость распределений (на пробе 11.11.2026 у первых пяти статей счёт слов совпал со снапшотом точно).

```bash
# панель: окно последних 35 суток (с запасом к горизонту 30 дней),
# реестр ведёт статьи до последнего горизонта, один прогон = одна волна
python collect_panel.py
python collect_panel.py --summary          # покрытие без сети
```

`collect_panel.py` — панельный сбор счётчиков свежих статей (входит и в публичный пакет): повторные наблюдения одних и тех же свежих статей в `data/panel/panel.jsonl` (append-only, одна строка = id + момент наблюдения). Время наблюдения фиксируется отдельно для каждого ответа сайта; реестр `data/panel/registry.json` ведёт статьи до последнего горизонта (по умолчанию 30 дней), статус обхода и признак достижения лимита страниц пишутся в `data/panel/run_status.json`; записи сохраняются порциями, сбой не теряет завершённую часть прохода. Ограничение: каждый запуск обновляет только статьи, найденные при обходе свежих страниц хабов. Реестр помнит статьи, но отдельно по идентификатору их не запрашивает, поэтому статья, выпавшая из обхода раньше горизонта, остаётся в панели с пропусками; `--summary` показывает, сколько статей дошло до каждого горизонта. Сборщик читает те же публичные счётчики, что и `01_fetch_metadata.py`: собственных данных он не содержит. Вежливый режим — последовательные запросы с паузой между страницами (`--sleep`, по умолчанию 1 c), повтор после 429 и явный `User-Agent: habr-analytics-research/...`; собранные данные не содержат чужих текстов. Рекомендуемый запуск раз в сутки:

```bash
# crontab: ежедневно в 03:17
17 3 * * * cd /path/to/habr_analytics && .venv/bin/python collect_panel.py >> data/panel/cron.log 2>&1
```

Эквивалент для systemd-таймера: unit `collect-panel.service` с `ExecStart=/path/to/.venv/bin/python collect_panel.py` и `collect-panel.timer` с `OnCalendar=*-*-* 03:17:00`. Через несколько недель панель даст честную цель «просмотры к N дням» без деления на возраст — именно её не хватает текущей модели. Целью считается наблюдение, ближайшее к горизонту внутри окна, без интерполяции.

## Ограничение архивного снимка в период реформы

Снимок собирался **9–10 ноября 2026 года**, одновременно с объявлением изменений типов публикаций Хабра. В сохранённых архивах можно проверить состав корпуса, значения `postType`, даты публикаций и правила фильтрации. При этом исходные HTTP-ответы и подробные логи того облачного сбора не сохранились; в исходных записях нет индивидуального `observed_at` (см. `data/input_manifest.json`). Поэтому невозможно полностью восстановить, как API классифицировал материалы в каждый момент переходного периода. Новые запросы к API показывают уже текущее состояние, а не историческое. Это **ограничение**, а не установленная ошибка собранного корпуса.
